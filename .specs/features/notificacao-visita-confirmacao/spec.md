# Notificação de Visita e Confirmação do Reparador Specification

## Problem Statement

When a promoter's route to a workshop (`RotaPromotor`) is created, the workshop has no way to learn about the visit, and nobody verifies that the address the promoter will drive to is still correct. Promoters arrive at closed, unaware, or relocated workshops. A WhatsApp notification carrying a lightweight, no-login link lets the reparador confirm both facts at once — that they know about the visit, and that their registered address is right — and correct the address on the spot when it is wrong.

Notifications must not become spam: a reparador who already has a live request or who confirmed recently is not messaged again, and a workshop whose record was updated in the last 3 months is not asked to re-confirm at all.

## Goals

- [ ] Every `RotaPromotor` creation attempts a WhatsApp notification to the workshop's reparador within the same request cycle, without blocking or failing route creation on notification failure.
- [ ] No reparador is messaged while they already have an outstanding request or a recent confirmation, and no workshop is asked to re-confirm an address that was updated within the last 3 months.
- [ ] A reparador can confirm the visit and their address — or correct the address — through a public, tokenized link; the outcome is persisted against the specific route and audited (who, when, from where).
- [ ] Confirmation status is visible to ops (dashboard) and to the promoter (app) as part of the existing route data, with no extra round-trip.

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
| --- | --- |
| Creating/approving the WhatsApp message template | `POST /messages/send-template` requires a pre-approved `templateName` on `wpp.oficinabrasil.com.br`. Template authoring/approval is business-side setup outside this codebase; the code reads the approved name from `WHATSAPP_TEMPLATE_NAME_VISITA` and fails closed until it's set. |
| Provisioning the WhatsApp account/token | `WHATSAPP_ACCOUNT_ID` and `WHATSAPP_API_KEY` are obtained from the `wpp.oficinabrasil.com.br` dashboard (Tokens tab), not generated by this feature. Code reads them from env and fails closed until set. |
| `/messages/bulk` (mass send) | This feature sends exactly one transactional message per route via `/messages/send-template` (`send:transactional` scope). Bulk sending is a different use case with its own job-status polling model. |
| SMS / email fallback channels | Only WhatsApp was requested. The channel interface (`camada de canais`) is built to support adding channels later without a redesign. |
| Automatic retry / backoff queue for failed sends | No background job, queue, or scheduler infrastructure exists anywhere in this codebase (`node-cron`/`node-schedule` are installed but unimported). Provider `RATE_LIMITED`/`QUOTA_EXCEEDED` responses are logged, not retried. |
| Consent gate / opt-in tracking of any kind | `Usuario.RECEBER_INFO` turned out not to be a usable consent signal (not reliably populated/scoped for this purpose), and no replacement field or collection flow exists. Product decision: MVP sends to any qualifying Usuario with a phone on file, no opt-in check. This is a deliberate scope cut, not an oversight — see Assumptions. |
| Mutating `dw.cadastro_empresa` | The `dw` schema is a read-only data warehouse in this codebase. Address corrections land on `MAIN_REGISTER.OFICINA` only; any downstream reconciliation into `dw` is someone else's pipeline. |
| Editing anything other than the address fields | The correction form exposes only `ENDERECO`, `NUMERO`, `COMPLEMENTO`, `BAIRRO`, `CIDADE`, `ESTADO`, `CEP`. A link-holder cannot alter phone, status, CNPJ, or any other `Oficina` column. |
| Re-geocoding a corrected address | `Oficina.LATITUDE`/`LONGITUDE` are left untouched by an address edit, so route optimization keeps using the last known coordinates. Re-geocoding needs a geocoding provider this codebase does not have (`getGeolocationDataByCep` resolves from the database, not an external API). Flagged as a known consequence — see Assumptions. |
| Approval workflow for address corrections | User's explicit call: edits write straight through to `Oficina`. No ops review queue. |
| Marketing / bulk notification campaigns | This is a transactional, one-route-one-notification flow, not a messaging campaign tool. |
| Reschedule (`reagendar`) implementation | User's explicit call: reserve the `REAGENDADO` STATUS value and the `/visita/reagendar` URL shape now, but ship no route or logic for it in this feature. |
| Reparador identity/login beyond one visit | The exchanged JWT is scoped to exactly one `NotificacaoVisita`/route (see Assumptions). A general reparador account/login system is not part of this feature. |

## User Stories

### P1: WhatsApp visit notification and public confirmation ⭐ MVP

**User Story**: As an Oficina Brasil operations user, I want a scheduled promoter visit to automatically notify the workshop's reparador via WhatsApp and let them confirm it through a secure public link, so that the team has a record the workshop is aware of and consents to the visit before the promoter arrives.

**Why P1**: This is the entire value loop the ticket chain exists to deliver. A notification nobody can confirm, or a confirmation flow with nothing feeding it, are each individually worthless — the loop only has value closed end-to-end.

**Acceptance Criteria** (each line is one EARS pattern):

1. WHEN a new `RotaPromotor` record is created THEN the system SHALL create exactly one `NotificacaoVisita` record in STATUS `PENDENTE` linked to that `ID_ROTA_PROMOTOR`.
2. WHEN resolving the notification recipient THEN the system SHALL select the `Usuario` linked to the route's `Oficina` with a non-empty `CELULAR`, ordering by `DATA_ALTERACAO` descending (most recent first, nulls last) and by `ID_USUARIO` ascending as a tiebreak, and SHALL take the first result.
3. IF no `Usuario` under the `Oficina` has a non-empty `CELULAR` THEN the system SHALL set the `NotificacaoVisita` STATUS to `FALHOU` with `ERRO_ENVIO` = `"no recipient with phone"` and SHALL NOT attempt a send.
4. WHEN a recipient is resolved THEN the system SHALL normalize `CELULAR` to the digits-only `55DDDNNNNNNNNN` format (country code + DDD + number, no `+` or separators) before dispatch, and IF the value does not fit a valid 10–11 digit Brazilian local pattern after the `55` prefix THEN the system SHALL treat the recipient as invalid and SHALL NOT dispatch.
5. WHEN a recipient with a valid normalized phone is resolved — before any dispatch attempt — THEN the system SHALL issue a signed link token bound to that `ID_NOTIFICACAO_VISITA` (opaque; re-exchangeable while valid, see AC15 — not itself single-use), set `EXPIRA_EM` to token-issuance time + 48 hours, and derive the public `confirmationUrl` from it, independent of whether the subsequent WhatsApp dispatch succeeds.
6. WHEN dispatching THEN the system SHALL `POST` to `{WHATSAPP_BASE_URL}/api/v1/messages/send-template` with header `Authorization: Bearer {WHATSAPP_API_KEY}` and body `{ accountId: WHATSAPP_ACCOUNT_ID, toPhone, templateName: WHATSAPP_TEMPLATE_NAME_VISITA, templateLanguage: "pt_BR", variables: [oficinaNome, confirmationUrl] }`, using the `confirmationUrl` issued in the previous step.
7. WHEN the WhatsApp API responds `200` with `success: true` THEN the system SHALL set `NotificacaoVisita` STATUS to `ENVIADO`, `ENVIADO_EM` to the current timestamp, and store the response's `messageId` and `providerMessageId`.
8. IF the WhatsApp API responds with `TOKEN_MISSING`, `TOKEN_INVALID`, `TOKEN_EXPIRED`, `ACCOUNT_DENIED`, `SCOPE_DENIED`, `ACCOUNT_NOT_FOUND`, or `TEMPLATE_NOT_FOUND` THEN the system SHALL set STATUS to `FALHOU` with `ERRO_ENVIO` = `"channel not configured"` and the provider's error code, treating it as a configuration problem rather than a per-recipient failure.
9. IF the WhatsApp API responds with `RATE_LIMITED` or `QUOTA_EXCEEDED` THEN the system SHALL set STATUS to `FALHOU` with `ERRO_ENVIO` capturing that code, without retrying.
10. IF the `RotaPromotor` creation transaction succeeds but the notification dispatch throws, times out, or the HTTP call itself fails THEN the system SHALL still return the created `RotaPromotor` successfully, isolating notification failure from the route-creation response.
11. WHERE `WHATSAPP_ACCOUNT_ID` or `WHATSAPP_TEMPLATE_NAME_VISITA` is not configured THEN the system SHALL skip the HTTP call, log the intended payload, and set STATUS to `FALHOU` with `ERRO_ENVIO` = `"channel not configured"` instead of raising an unhandled exception (the confirmation token from step 5 still exists and remains valid even though the message was never delivered).
12. The system SHALL NOT perform the outbound WhatsApp HTTP call unless `WHATSAPP_SEND_ENABLED` is exactly `"true"`; when unset or any other value, the channel SHALL take the no-op path (log payload, `FALHOU` / `"channel not configured"`) the same as missing account/template config.
13. WHILE `NODE_ENV` is `"test"` the system SHALL take the no-op path unconditionally — regardless of `WHATSAPP_SEND_ENABLED`, `WHATSAPP_ACCOUNT_ID`, or `WHATSAPP_TEMPLATE_NAME_VISITA` — so automated test runs can never perform a real send.
14. WHEN the frontend calls `GET /visita/{token}` with a link token whose `NotificacaoVisita` STATUS is `ENVIADO` and unexpired THEN the system SHALL issue a short-lived JWT (30 minutes, scope `visita:confirmar`, subject = `ID_USUARIO`, claims include `ID_NOTIFICACAO_VISITA` and `ID_ROTA_PROMOTOR`), signed with the existing `JWT_SECRET` via `jsonwebtoken` (same library/pattern as promoter login), and SHALL return it together with the Oficina name and visit date.
15. WHILE a `NotificacaoVisita` is in STATUS `ENVIADO` and unexpired, the system SHALL allow the same link token to be exchanged for a fresh JWT on every call to `GET /visita/{token}` (page reloads, re-opening the WhatsApp link) — only the `CONFIRMADO` transition is single-use, not the page view or the exchange.
16. IF the link token is malformed or fails signature verification THEN `GET /visita/{token}` SHALL respond with a distinct `TOKEN_INVALID` state and SHALL NOT issue a JWT.
17. IF the linked `NotificacaoVisita`'s `EXPIRA_EM` has passed THEN `GET /visita/{token}` SHALL report its effective status as `EXPIRADO` (per AC22) and respond with a distinct `EXPIRED` state, and SHALL NOT issue a JWT.
18. IF the linked `NotificacaoVisita` STATUS is already `CONFIRMADO` THEN `GET /visita/{token}` SHALL respond with a distinct `ALREADY_CONFIRMED` state (including `CONFIRMADO_EM`) and SHALL NOT issue a JWT.
19. WHEN the reparador submits `POST /visita/confirmar` with header `Authorization: Bearer {jwt}` THEN the system SHALL validate the JWT's signature, expiry, and `visita:confirmar` scope; re-check the linked `NotificacaoVisita` is still STATUS `ENVIADO` and unexpired; and SHALL atomically transition it to `CONFIRMADO`, setting on that same row `CONFIRMADO_EM` (timestamp), `CONFIRMADO_POR` (= the JWT's `sub`/`ID_USUARIO`), and `CONFIRMADO_IP` (source IP of the request).
20. IF a JWT presented to `POST /visita/confirmar` is expired, has an invalid signature, lacks the `visita:confirmar` scope, or its linked `NotificacaoVisita` is no longer `ENVIADO` THEN the system SHALL reject the confirmation, return an `ALREADY_CONFIRMED` or `TOKEN_INVALID` response as appropriate, and SHALL NOT alter STATUS.
21. IF two `POST /visita/confirmar` requests for the same `NotificacaoVisita` are received concurrently THEN the system SHALL apply exactly one `CONFIRMADO` transition and SHALL return an `ALREADY_CONFIRMED` response to the other.
22. WHILE a `NotificacaoVisita` is in STATUS `ENVIADO` and its `EXPIRA_EM` has passed without confirmation, the system SHALL treat both the link token and any previously issued JWT as invalid for confirmation, and SHALL report its effective status as `EXPIRADO` on **every** read path — the exchange endpoint and the dashboard/app views alike — derived at read time from `STATUS` + `EXPIRA_EM` rather than from a stored transition, so a link nobody ever opens is never reported as still live.
23. WHERE a future reschedule capability is added, the `NotificacaoVisita` STATUS enum SHALL reserve a `REAGENDADO` value now, and the confirm endpoint's URL SHALL be shaped as one action (`/visita/confirmar`) alongside a reserved sibling (`/visita/reagendar`) so the reschedule action can be added later without changing the exchange (`GET /visita/{token}`) or confirm contracts. No `reagendar` route or STATUS-setting logic ships in this feature.
24. The system SHALL log `NotificacaoVisita` creation, link-token issuance, JWT exchange, dispatch attempt, dispatch result, and confirmation events to the console with `ID_ROTA_PROMOTOR` and `ID_NOTIFICACAO_VISITA` for traceability.
25. The system SHALL reject more than 20 requests per minute targeting the same visit — keyed on the link token for `GET /visita/{token}` and on the JWT's `ID_NOTIFICACAO_VISITA` claim for the authenticated `POST`/`PUT` actions — so no single visit's confirmation link can be hammered, independent of the caller's source IP.

**Pre-send guards** (evaluated in the send flow before AC4's phone normalization; numbered after the criteria above only to keep existing requirement cross-references stable):

26. IF the route's `Oficina` has a `DATA_ALTERACAO` within the last 3 months THEN the system SHALL set the `NotificacaoVisita` STATUS to `DISPENSADO` with `ERRO_ENVIO` = `"address recently updated"`, and SHALL NOT resolve a recipient or attempt a send.
27. WHEN evaluating the anti-spam guards for a resolved recipient THEN the system SHALL first persist STATUS `EXPIRADO` to every `NotificacaoVisita` belonging to that `Usuario` that is in STATUS `ENVIADO` with `EXPIRA_EM` already passed, so an expired row is never counted as outstanding by AC28.
28. IF the resolved recipient `Usuario` has any `NotificacaoVisita` in STATUS `ENVIADO` whose `EXPIRA_EM` has not passed — on any `Oficina` — THEN the system SHALL set the new row's STATUS to `DISPENSADO` with `ERRO_ENVIO` = `"recipient has outstanding notification"` and SHALL NOT attempt a send.
29. IF the resolved recipient `Usuario` has any `NotificacaoVisita` in STATUS `CONFIRMADO` with `CONFIRMADO_EM` within the last 3 months — on any `Oficina` — THEN the system SHALL set the new row's STATUS to `DISPENSADO` with `ERRO_ENVIO` = `"recipient confirmed recently"` and SHALL NOT attempt a send.

**Address confirmation and correction:**

30. WHEN `GET /visita/{token}` returns a `PENDING` state THEN the system SHALL include the workshop's name and its current registered address (`ENDERECO`, `NUMERO`, `COMPLEMENTO`, `BAIRRO`, `CIDADE`, `ESTADO`, `CEP`) so the reparador can check it, and SHALL NOT include any visit date.
31. WHEN the reparador submits `PUT /visita/endereco` with a valid `visita:confirmar` JWT and a corrected address THEN the system SHALL update only the address columns of the linked `MAIN_REGISTER.OFICINA` row, SHALL apply the same `ENVIADO`→`CONFIRMADO` transition and audit fields as AC19, and SHALL set `ENDERECO_ATUALIZADO` to true on the `NotificacaoVisita`.
32. IF a `PUT /visita/endereco` request carries any field outside the address column allowlist THEN the system SHALL reject the request with a validation error and SHALL NOT write to `Oficina`.
33. IF the `Oficina` address update fails at the database level (including a missing `UPDATE` grant on `MAIN_REGISTER`) THEN the system SHALL leave `NotificacaoVisita` STATUS unchanged, SHALL NOT report the confirmation as successful, and SHALL surface a distinct error state to the caller.

**Independent Test**: Create a `RotaPromotor` for an Oficina whose `Usuario` has `CELULAR` set; confirm a `NotificacaoVisita` row appears `PENDENTE` → `ENVIADO` via a real (or `WHATSAPP_TEMPLATE_NAME_VISITA`-unset-stubbed) call to `wpp.oficinabrasil.com.br`. Call `GET /visita/{token}`, verify it returns a JWT plus Oficina name/date. Call `POST /visita/confirmar` with that JWT, verify STATUS = `CONFIRMADO` and audit fields are set. Call `GET /visita/{token}` again and confirm it now returns `ALREADY_CONFIRMED` without issuing a JWT or changing state.

### P2: Visit-confirmation status visibility

**User Story**: As an internal ops/dashboard user and as the promoter in the field, I want to see whether a workshop has confirmed its scheduled visit, so that I know which stops are ready before or during the route.

**Why P2**: A valuable feedback loop, but it is a read-only projection of state P1 already persists — the core notify→confirm mechanics work and are independently verifiable via direct API inspection without this surface.

**Acceptance Criteria**:

1. WHEN the dashboard requests route details for a `RotaPromotor` THEN the system SHALL include the linked `NotificacaoVisita` STATUS and `CONFIRMADO_EM` (if set) in the response.
2. WHEN the promoter app requests a promoter's route list THEN the system SHALL include each route's visit-confirmation STATUS in the same `{ message, data }` envelope shape used by existing route endpoints.

**Independent Test**: Confirm one route via the P1 flow, leave another `PENDENTE`. Call the dashboard/app route endpoints and verify the confirmed route shows `CONFIRMADO` with a timestamp and the other shows `PENDENTE`/`ENVIADO`.

## Edge Cases

- IF the route's `Oficina` has zero linked `Usuario` records THEN the system SHALL set `NotificacaoVisita` STATUS to `FALHOU` with `ERRO_ENVIO` = `"no usuario linked to oficina"`.
- IF `CELULAR` contains non-numeric characters or an invalid DDD THEN normalization SHALL fail closed (no dispatch), not send to a malformed number.
- WHEN a link token past its `EXPIRA_EM` is opened THEN the system SHALL show the expired state and SHALL NOT accept a confirmation submission against it.
- IF a second `RotaPromotor` is created for the same Oficina before the first is confirmed THEN the system SHALL create a second, independent `NotificacaoVisita` row (uniqueness is per `ID_ROTA_PROMOTOR`, not per Oficina).
- IF the WhatsApp API is unreachable (network error, timeout, non-JSON response) THEN the system SHALL treat it the same as a documented error response — STATUS `FALHOU`, route creation still succeeds.
- IF a JWT was validly issued before `EXPIRA_EM` passed but is presented to `POST /visita/confirmar` after it has passed THEN the system SHALL still reject it — the confirm endpoint re-checks live `NotificacaoVisita` STATUS/expiry rather than trusting the JWT's snapshot at issuance time.
- Outstanding, unused JWTs are not individually tracked or revoked; once `NotificacaoVisita` STATUS leaves `ENVIADO` (via `CONFIRMADO` or `EXPIRADO`), the live STATUS check on confirm makes any earlier JWT for it ineffective without needing a revocation list.
- IF a test run somehow has `WHATSAPP_SEND_ENABLED=true` in its environment THEN the `NODE_ENV=test` lock SHALL still prevent a real call — the test-env lock takes priority over the enable flag, not the other way around.
- WHEN a batch of routes is created for several workshops sharing one recipient `Usuario` THEN only the first SHALL send; the rest SHALL be `DISPENSADO` / `"recipient has outstanding notification"` — the anti-spam guard is evaluated per route against live state, so ordering within the batch decides which one wins.
- IF a reparador corrects their address THEN `Oficina.DATA_ALTERACAO` is bumped by the `@UpdateDateColumn`, which by AC26 suppresses further notifications to that workshop for 3 months — intended, and the mechanism by which a correction stops the nagging.
- IF the corrected address moves the workshop to a genuinely different location THEN `LATITUDE`/`LONGITUDE` remain stale (no geocoding provider exists), so `findNearestOficinas` and route optimization keep using the old coordinates until someone re-geocodes.
- IF `Oficina.DATA_ALTERACAO` is NULL THEN the address SHALL be treated as stale (not fresh) — the freshness guard only skips on a positive, recent timestamp, never on absence of one.

## Success Criteria

How we know the feature is successful:

- [ ] A `RotaPromotor` created for a phone-equipped `Usuario` results in a real call to `wpp.oficinabrasil.com.br` (or a clearly logged "channel not configured" skip if account/template env vars are unset) within the same request cycle, without failing route creation.
- [ ] A reparador can open the confirmation link, exchange it for a JWT, and confirm within the 48h link window — reflected as `CONFIRMADO` within one `GET` + one `POST` round-trip.
- [ ] Reused, expired, or malformed tokens/JWTs are rejected 100% of the time in tests without mutating STATUS.
- [ ] The frontend contract (endpoints, states, JWT handling) is documented well enough that a frontend agent can implement the confirmation page without reading backend source.
- [ ] Dashboard and promoter-app route responses include current `NotificacaoVisita` STATUS with zero additional round-trips.
